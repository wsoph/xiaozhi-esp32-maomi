# Session A｜从零开始到交接的事实底稿

## 1. Session 范围

- 本 session 的具体目标：
  - 检查现有小智 AI 机器人资料和硬件能力。
  - 备份原机固件，建立可恢复到购买状态的方案。
  - 下载、编译并试刷官方 2.4.2。
  - 了解并实践云端 MCP，增加电脑静音和解除静音能力。
  - 将机器人逐步改造成名为“小猫咪”的桌面宠物核心交互原型。
  - 加入“猫咪过来”唤醒词、猫咪人设、猫咪表情、互动动画、声音、亲密度、提醒和安静模式等能力。
  - 当前设备形态是开发板加 1.54 英寸屏幕，不是带完整外壳的最终产品。

- 本 session 开始时的机器人状态：
  - Wi-Fi 版本、1.54 英寸 TFT 屏幕。
  - 已完成配网，可以正常对话。
  - 闲置进入困倦表情后，实测无法用唤醒词唤醒，需要按键。
  - 使用的是购买时预装固件，尚未建立本地源码开发、固件备份和回滚流程。
  - 用户明确表示自己是智能硬件新手。

- 为什么需要 handover：
  - 会话剩余 context 约为 14%。
  - RC3 修复已经写完并通过主机测试，但完整 ESP32-S3 编译中断。
  - 后续仍需完成编译、代码复核、发布包、刷机和真机测试，继续依赖超长对话不利于准确续接。
  - 因此创建了独立交接文件，供新 session 从明确状态继续。

- handover 创建时已经完成：
  - 原机固件备份和恢复文档。
  - 官方 2.4.2 下载、编译、刷入及基础功能验证。
  - 电脑静音和解除静音 MCP 的实现与一次真机验证。
  - “小猫咪”名称、人设和“猫咪过来”唤醒词的确定。
  - 需求规格、验收记录和开发任务清单。
  - 猫咪静态表情、动画和本地声音素材管线。
  - RC1、RC2 的编译、刷入和部分真机验收。
  - RC3 的互动猫叫时序修复及 `111/111` 主机测试。

- handover 创建时仍未完成：
  - RC3 完整编译。
  - RC3 Git 提交、发布包和 SHA-256 校验。
  - RC3 刷机。
  - 摸摸、喂食、陪玩三个动作的“动画＋独立猫叫”最终真机验收。
  - 机器人外壳设计。
  - MCP 服务异常退出后的可靠自动恢复。
  - 若干提醒动画、亲密度持久化和自主动作的完整回归验证。

## 2. 真实时间顺序

1. 用户先让 Codex 阅读本地客户资料，确认设备为 Wi-Fi 版、1.54 英寸 TFT，并已完成配网。

2. 用户询问充电、充电指示灯、电池使用和困倦状态。后续真机只确认了：
   - 接入 USB 时屏幕出现充电符号。
   - 拔掉 USB 后设备可继续由电池供电。
   - “绿色是否代表充满”和长期电池养护结论，本 session 没有通过硬件资料或真机实验最终确认。

3. 用户确认困倦表情出现后，唤醒词不起作用，需要按键，并要求查看源码。

4. 修改前先建立恢复能力：
   - 尝试通过 USB 连接机器人。
   - 经历过数据线、串口识别、BOOT 操作和连接失败等多次重试。
   - 用户亲自找到 BOOT 键、安装驱动、重新插拔设备并按住或短按实体按键。
   - 最终保存了原机 16 MiB Flash 备份，并保留 SHA-256 校验记录。
   - 创建了把备份刷回、恢复购买状态的详细文档。

5. Codex检查官方 GitHub 仓库和本地源码资料：
   - 下载官方最新版源码。
   - 比较官方源码与设备现有状态。
   - 为 1.54 英寸 Wi-Fi 硬件进行编译适配检查。
   - 解释“源码为什么要编译成设备可执行固件”。

6. 试刷官方 2.4.2：
   - 刷机前多次进入下载模式失败，需要用户重新插线、按住 BOOT 和控制开机。
   - 用户明确决定不再重复备份，直接刷新版本。
   - 刷入后重新配网。
   - 基础测试通过。
   - 一度出现中文识别很差，最后确认原因是设备语言被设置为英语；改成中文后恢复正常。

7. 测试云端 MCP：
   - 官方计算示例已经连接，但实际算数请求没有出现 MCP 调用记录。
   - 用户要求实现一个机器人原本无法直接完成的操作：修改电脑系统音量状态。
   - Codex编写了电脑静音和解除静音两个 MCP 工具。
   - 用户完成 MCP endpoint 配置和设备语音测试。
   - 静音、解除静音均曾实际生效。
   - 后续设置了开机自动启动方案，并把自定义 MCP 放入独立目录。
   - 之后服务曾意外退出，计划任务没有自动恢复；人工重启后功能再次正常。可靠性问题在 handover 时仍未关闭。
   - 会话中出现过带 Token 的 WebSocket endpoint；该信息不能公开。

8. 确定桌面宠物方向：
   - 最初考虑“咪咪过来”，之后因名称含义问题，要求全部替换。
   - 最终宠物名称确定为“小猫咪”。
   - 唤醒词确定为“猫咪过来”。
   - 预期固定回应为猫叫或“喵喵”。
   - 安静时段确定为 22:00—08:00。
   - 暂时不增加额外硬件。
   - 外壳未来只露出屏幕；正常宠物互动不依赖按键。
   - 配网、音量和故障恢复仍允许把设备从外壳取出后使用实体按键。

9. 创建并修改猫咪人设：
   - 初次询问“你是谁”时，机器人回答“我是小智”。
   - 用户把猫咪人设保存到云端设备配置。
   - 再次测试后，机器人能够回答“我是小猫咪”。
   - 人设保存在独立 Markdown 文档，计划后续继续优化。

10. 进入规格和源码实现阶段：
    - 先完成模块规格、验收条件和任务计划。
    - 使用 Codex 组织测试驱动开发、分阶段实现、代码复核和 Git 保存点。
    - 建立独立的小猫咪板型，而不是覆盖原始 1.54 英寸板型。
    - 接入自定义唤醒模型、中文字体、Assets 管线、猫咪状态和互动逻辑。
    - 多轮代码复核出现过重试、分两次复核以及修复后再次复核。

11. 制作猫咪视觉：
    - 先制作多个视觉方向，用户选择 A 方案。
    - 用户确认表情可以放大到约半屏，并去掉字幕。
    - 制作了 21 种静态猫咪表情和 9 类设备专属动画。
    - 用户确认视觉效果良好。
    - 真机后来显示过猫咪充电图案、被摸、进食、玩耍和提醒动画。

12. 制作本地声音：
    - 第一轮提供了四段声音。
    - 用户认为除 `prompt` 外，其余声音差异小且太短。
    - 用户提供两个视频格式的候选素材，Codex将其转换为适合设备使用的音频。
    - 用户保留两个声音，并手动把 `prompt` 替换成第二轮较长版本。
    - 这一步包含用户主观试听、选择和手动替换，并非全自动。

13. RC1 刷机及真机测试：
    - 用户明确授权刷入 RC1，并亲自连接设备、按住 BOOT。
    - 设备正常启动，显示猫咪充电图案，播放过猫叫并切换表情。
    - 正常语音问答可用。
    - 摸摸、喂食和陪玩工具会回答“已经排队”，但在持续聆听状态下没有立即播放专属动画。
    - 按 BOOT 退出聆听后，能看到被摸、进食或玩耍动画。
    - 三种互动当时均没有听到预期的独立互动猫叫。
    - 屏幕曾直接显示 `self.pet.interact`，属于不应面向用户展示的内部工具文字。
    - 陪玩后亲密度增加到 14 分。
    - 提醒功能存在不同结果：有一次提醒动画和提示音均出现；指定闹钟曾只有提示音、没有动画。
    - 周期提醒最短间隔实测为 10 分钟。
    - 创建、查询和取消倒计时、喝水提醒、番茄钟、久坐提醒等状态操作曾通过。
    - 关机重启后，亲密度从 17 变回 14，证明短时间内的亲密度增量没有可靠落盘。
    - 观察 60 秒后屏幕会变暗，但眨眼、张望未明显出现，睡眠动画时有时无。
    - 安静模式能开启；关闭时语音曾误说成“不在按键模式”。

14. RC2 集中修复和刷机：
    - 修复持续聆听覆盖宠物动画的问题。
    - 调整提醒和互动的界面优先级。
    - 调整亲密度重要写入策略。
    - 延长自主动作和睡眠动画的显示窗口。
    - 尝试让本地猫叫播放期间暂停语音上传，避免机器人听到自己的猫叫。
    - 用户明确授权刷入 RC2，并完成 BOOT 操作。
    - RC2 能正常启动。
    - 自然说“摸摸小猫咪”后，不再需要按键，自动出现被摸动画。
    - 但没有播放独立的 `maomi_meow.ogg`，只说了“喵好舒服呀”。

15. RC3 根因定位和源码修复：
    - 确认云端语音回复正在占用音频播放队列。
    - 本地猫叫等待队列空闲时，原 4 秒互动生命周期已经到期，待播放猫叫随之被清除。
    - RC3 增加了互动音频等待策略：
      - 等待猫叫时暂停互动生命周期倒计时。
      - 最长等待 15 秒。
      - 猫叫成功入队后重新给予完整 4 秒动画时间。
      - 处理单调时钟回退。
    - 新增行为回归测试。
    - 完整主机测试为 `111/111` 通过。
    - 格式检查和 `git diff --check` 通过。

16. RC3 完整编译中断：
    - 首次环境问题是通用导出脚本指向不存在的 Python 环境。
    - 后续又遇到缺少 `IDF_PATH`。
    - 补齐后 CMake 已识别 ESP-IDF 6.0.2、ESP32-S3、小猫咪板型和 Assets。
    - Ninja 进入大规模编译，但最终进程已经停止。
    - handover 前检查不到 `xiaozhi.bin` 和 `xiaozhi.elf`。
    - 没有保存到明确的最终编译错误，因此只能确认“编译被中断”，不能确认“RC3 源码无法编译”。

17. 创建 handover：
    - 记录当前真机版本、RC3 修改、测试证据、未提交文件、编译中断点、工具链注意事项、下一步和刷机授权边界。
    - handover 创建时机器人仍运行 RC2。

## 3. 本 session 实际完成的功能

### 唤醒词与猫叫

- 修改了什么：
  - 将目标唤醒词确定为“猫咪过来”。
  - 接入自定义唤醒 Assets。
  - 增加本地唤醒回应和互动猫叫素材。
  - 清理此前“咪咪”相关命名。

- 实现方式：
  - 使用板型专属 Assets 管线打包唤醒模型、文字资源和 OGG/Opus 音频。
  - 唤醒回应和互动猫叫使用不同本地资源。

- 验证方式：
  - 用户多次真机说“猫咪过来”。
  - 设备能被唤醒，并能在播报中被唤醒词打断。
  - RC1 启动后用户观察到猫叫和表情变化。

- 当前效果：
  - “猫咪过来”能够唤醒设备。
  - 一次明确测试中设备回答的是“喵，我过来了”，并非预期的固定“喵喵”。
  - RC2 的独立互动猫叫仍未播放。

- 限制或未完成部分：
  - 本 session 没有最终确认唤醒后每次都只播放固定“喵喵”。
  - RC3 的猫叫时序修复尚未刷入真机。

### 猫咪表情

- 修改了什么：
  - 选择 A 方案猫咪形象。
  - 表情放大到约半屏。
  - 去除字幕。
  - 制作 21 种静态表情和 9 类专属动画。

- 实现方式：
  - 通过自定义 Assets 加入 PNG、GIF、字体和表情映射。
  - 为充电、低电量、提醒、被摸、进食、玩耍、眨眼、张望和睡眠等状态设置专属资源。

- 验证方式：
  - 用户先审核视觉稿。
  - 刷机后直接观察屏幕。
  - 真机显示过猫咪充电图案、被摸、进食、玩耍和提醒动画。

- 当前效果：
  - 猫咪视觉方向得到用户确认。
  - 多种专属动画已经能够在真机显示。

- 限制或未完成部分：
  - RC1 中部分动画需要按 BOOT 结束聆听后才出现。
  - RC2 只明确复测了被摸动画自动出现。
  - 睡眠动画仍有时无。
  - 外壳尚未设计，当前只是开发板加屏幕的视觉原型。

### 摸摸互动

- 修改了什么：
  - 增加摸摸意图、互动事件、被摸动画、亲密度增量和互动猫叫。
  - RC2 修复持续聆听遮挡动画。
  - RC3修复猫叫等待队列时序。

- 实现方式：
  - 云端识别用户语义后调用设备侧宠物互动工具。
  - 设备把互动事件加入本地队列，再触发表情、动画、声音和状态更新。

- 验证方式：
  - RC1 中说“摸摸小猫咪”，观察回复和屏幕。
  - 按 BOOT 后确认被摸动画存在。
  - RC2 中自然说同样指令，确认无需按键即可自动出现动画。

- 当前效果：
  - RC2 已实现无需按键自动播放被摸动画。
  - 机器人会说“喵好舒服呀”。

- 限制或未完成部分：
  - RC2 没有播放独立互动猫叫。
  - RC3 修复尚未真机验证。

### 喂食互动

- 限制或未完成部分：

  - 没有听到独立猫叫。
  - RC2、RC3 的最终喂食回归，本 session 未确认。

### 语音游戏

- 限制或未完成部分：
  - RC1 仍依赖按键结束聆听。
